# 0008 — One-Click Bootstrap Wizard, Loopback Session, Cupbearer-Supervised Form (2026-11-12)

## Status

Accepted (implemented + measured in the Cupbearer's clean-environment E2E)

## Context

The author ruled that first-run initialization must be "one entry, one click"
and live in THIS panel (the Cupbearer's operation surface), with the Cupbearer
auto-launching the panel so operators never deploy it separately. This entry
records the MV side of that work; the engine semantics are normative in
HA-Cupbearer
`knowledge/0016-first-run-bootstrap-mv-autostart-infra.md`.

## Decision

### Wizard (`frontend/src/WizardView.tsx` + `frontend/src/wizard/`)

First-use wizard, default tab ("首次使用向导"); the advanced
"编排操作（高级）" tab stays as the direct entry for experienced users.
Seven steps (`frontend/src/wizard/state.ts::STEP_ORDER`): deploy path
(explicit single choice bare-metal/container — one deployment walks one
path, and the choice drives which target forms/execution entry render) →
environment self-check (aggregates the read-only endpoints; 503 and probe
failures become checklist items with an actionable next step) → secrets &
initialization (the original bootstrap form — infra cards with BOTH
connection forms and one-click launch, the six public URLs as the only
human inputs, preview (`POST /api/bootstrap/plan`) and one-click run
(`POST /api/bootstrap/run`) with per-step progress, masked fingerprints,
notes, retry-as-resume; target forms follow the chosen path, no more dual
checkboxes; since contract 1.6.0 a database-conflict disposition — three
selectable cards skip/reuse/takeover with plain-language consequences, skip
preselected and reasoned, reuse revealing a required existing-password
field, plus full admin connection / MySQL / Redis host-port overrides in the
advanced section, so a pre-existing app account on a different password is
resolved explicitly instead of failing mid-run) → artifact sources
(declared `artifact_source` per project
since contract 1.5.0, four-source prerequisite guide, manifest-gap /
validation-failure detection with schema pointers and an in-UI
deploy-manifest skeleton generator with inferred scan roots) → preflight
(blockers carry per-name next actions) → execute (bare-metal deploy runs
with dry-run default, or the container stack trigger) → health
confirmation (declared=active + healthy as the terminal check). Every step
goes back, can be skipped (tracked and shown), and explains why it exists.
Wizard state (current step + human inputs) persists in localStorage
(`mv-wizard-state-v1`) so refresh/reopen resumes; backend run records stay
the server's resume mechanism. The whole panel is keyboard-operable:
Enter/Space on a focused button/checkbox activates it through an explicit
app-level keydown handler (`frontend/src/App.tsx`) that adopts the default
action (preventDefault first, so normal browsers never double-fire).
Client-side blocking: empty/invalid URLs
show plain-language errors on submit attempt; server-side field errors
(upstream 400 `data.field_errors`) render as a blocker list. Advanced
section collapsed (external-MySQL admin password; everything else
backend-derived).

### Proxy layer (`internal/server/handlers_bootstrap.go`)

`/api/bootstrap/*` mirrors the Cupbearer's `/api/v1/deploy/bootstrap/*`
(contract: ha-cupbearer.yaml v1.3.0) with the established pattern:
server-side token injection (`X-Deploy-Token`), raw `data` passthrough,
typed upstream-error translation, request log metadata only. Infra one-click
endpoints get a 5-minute client timeout (they wait for real readiness).

### Loopback session (`server.loopback_session`, config additive)

Default false (zero regression for standalone deployments). When true — the
form generated by the Cupbearer's MV manager — requests from loopback
addresses skip the login gate (`authMiddleware`, `SessionStatus` report
`auth_required=false` to them). Trust model: the panel is pinned to
127.0.0.1 in this form; loopback trust equals the operator's local/SSH-tunnel
access, the same level as the historical no-token mode. The deploy token is
still injected server-side into mutating proxy calls and never reaches the
browser; the Cupbearer's endpoints stay fail-closed regardless.

### Cupbearer-supervised lifecycle (MV side responsibilities)

MV needs nothing special to be supervised: it reads `config.yaml` from its
working directory (generated by the Cupbearer: listen address,
`cupbearer.base_url`, `cupbearer.token`, `frontend_dist`,
`loopback_session: true`), serves the frontend from `frontend_dist`, and
exposes `/healthz` for the supervisor's probes. Shutdown on SIGTERM is
graceful (gin server exit). Standalone form (compose service or manual) is
unchanged.

## Consequences

- Measured E2E (clean environment, 2026-11-12): panel auto-launched by the
  Cupbearer (managed child, pid reported at `/api/v1/deploy/maintenance-view`),
  no login screen on loopback, wizard one-click ran infra → secrets →
  databases → keys → `.env` → renders; composed service stack came up healthy
  against the ha-infra MySQL/Redis; re-run fully idempotent; mid-run kill resumed.
- The supervised MV's deploy token comes from the Cupbearer's credentials
  file (auto-generated there on first start) — operators never type it.
- The legacy `BootstrapView.tsx` was removed (2026-11-12) once the wizard
  replaced it; its backend endpoints stay for compatibility this revision.
  The old WIP knowledge entries (0001/0004/0006) are archival snapshots with
  anchors demoted to plain text.
